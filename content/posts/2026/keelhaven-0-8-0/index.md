8月31日我发布了 Keelhaven 0.5.0，9月3日在这里写了[一篇文章](../keelhaven/index.md)介绍它。九天之后，0.8.0 发布了。

这九天里其实还发了 0.6.0 和 0.7.0——功能到了就发，没等攒大版本。加进去的东西，基本没有一件在我原来的计划里。有人在 X 上转发，有人发邮件，有人直接把 issue 当聊天框用。其中两位贡献了大半工作量：一位一口气报了五个问题，两个 bug 三个需求；另一位从命令行 restic 搬过来，一封信列了他每天在用的参数。

下面按反馈的来源讲：我自己撞上的一个 bug、一个目的地的请求、一个参数请求、一个装了五条反馈的 issue、一封老用户的信、一个 Backblaze B2 的坑，最后是我拒绝掉的两件事。

---

## 先说一个我自己撞上的 bug

0.5.0 发出去之后，我在自己机器上删一个测试计划：确认弹窗点了删除，Touch ID 也按了，然后那一行还在。重开菜单还在，重启 App 才消失。

看起来像是列表没刷新。实际上删除函数第一行是这么写的：

```swift
guard !isResticBusy else { return }
```

只要 App 里**任何一个** restic 进程在跑，一次已经确认过、已经验过指纹的删除就直接返回，屏幕上不留任何痕迹。

而这个窗口非常好撞：一次备份跑完会紧接着自动跑 `restic check`。所以「立即备份 → 看它跑完 → 删除」这个再自然不过的顺序，删除正好落在 check 里面。点的时候菜单项是可用的，几秒钟之后指纹验完，守卫才生效。

改法是把范围收窄：只有这个计划自己的 restic 在跑时才拒绝。那是拔掉凭据可能让目的地不一致的唯一情况；别的计划在跑是另一个进程、另一份密钥，不相干。而且拒绝要说出来，现在会弹一个提示说这个计划正在忙，而不是把用户刚批准的破坏性操作悄悄吞掉。

我很不喜欢这个 bug 的形态。它是一个静默失败，正好长在备份软件最不该静默失败的地方。修复[跟着 0.6.0 一起发了出去](https://github.com/shenxianpeng/keelhaven/pull/31)。

## 有人想备份到自己的 rest-server

0.5.0 支持三种目的地：本地硬盘、S3 兼容存储、SFTP。发布之后有人问 [rest-server](https://github.com/restic/rest-server)。

这个请求很合理，因为 rest-server 就是 restic 官方给家用服务器和 NAS 推荐的后端。用 SFTP 指向同一台机器当然也能跑，但会丢掉 rest-server 的 append-only 模式，而那正是不少人选它的原因。

0.6.0 加了这个目的地：填 URL、用户名、密码。密码进钥匙串，通过 `RESTIC_REST_USERNAME` / `RESTIC_REST_PASSWORD` 传给 restic 子进程，不出现在命令行参数里，和 S3、SFTP 是同一条规矩。用户名留空表示完全不认证，对应 `rest-server --no-auth`，这种情况下不会创建钥匙串条目。

第一版只支持 rest-server 的默认模式：不带 `--private-repos`，不带 `--append-only`，不支持自签名证书。提这个需求的人就是这么跑的，我没有去猜别人可能还需要什么。

## 「建议增加一些高级参数自定义的添加」

这是 [issue #37](https://github.com/shenxianpeng/keelhaven/issues/37) 的原话，点名了三个：`--pack-size`、`--read-concurrency`、`--limit-upload`。

最省事的做法是加一个「额外参数」输入框，让高级用户自己填。但它会坏掉几件正在承重的东西：

- `--quiet` / `--verbose` 会改变 restic 的 `--json` 事件流，而 App 里每一个进度条、每一条运行摘要都是从这个流里解析出来的
- `--no-lock` 会绕过「同时只跑一个 restic」的保护
- `--insecure-tls` 会静默关掉证书校验。一个备份工具不该有一个开关，能让它悄悄不再验证自己在跟谁说话

还有一条更现实的：任意字符串没有可定义的行为，写不出测试，而 CI 对核心库强制 100% 行覆盖。

所以 0.7.0 的做法是把这三个做成**具名字段**，每个带自己的标签、自己的校验范围、自己的测试：

| 字段 | 对应参数 | 校验 |
|---|---|---|
| 上传限速 | `--limit-upload` | KiB/s，留空即 restic 默认 |
| 同时读取的文件数 | `--read-concurrency` | 1–32 |
| Pack 大小 | `--pack-size` | 4–128 MiB |

这三个都不是凑数的。`--limit-upload` 是唯一能阻止首次全量备份把家里上行带宽占满的东西，restic 连对应的环境变量都没有；`--read-concurrency` 的默认值 2 在两个方向上都不对，对外置机械盘太高，对 NVMe 太低；`--pack-size` 在按请求次数计费的对象存储上是真金白银。

夹紧范围的代码写在核心库里，不在输入框上。因为界面那一层没有测试能覆盖到，而一份手工改过的 `plans.json` 不该能塞进一个 restic 会拒绝的值。

## 一个 issue 里装了五条反馈

然后 [#39](https://github.com/shenxianpeng/keelhaven/issues/39) 来了，标题是「有几个就一起反馈吧~」，里面两个 bug 三个需求，还配了张截图。我把它拆成五个子 issue，修了四个，剩下一个还开着。

### 编辑窗口卡住了

展开高级设置以后，编辑计划的窗口变得特别长，拖不动，也缩不了，保存按钮跟着掉到屏幕外面去。

原因有两个：没有滚动视图；窗口用了 `.windowResizability(.contentSize)`，内容顶到多高它就是多高，用户改不了。

改完是：各区块放进 `ScrollView`，保存和取消固定在下面不跟着内容滚，窗口默认 560×640 并且可以自由缩放。

还有一处藏得比较深：文件夹列表和排除规则列表原本是 `List`。`List` 套在 `ScrollView` 里会带来第二个滚动条，鼠标停在上面时滚轮就被它吃掉，正好就是那句「就卡在这里」。所以它们改成了普通的带边框行。

### 「必须强制备份一次后才能进一步编辑，不符逻辑」

这条我一开始以为是误会，因为「编辑计划」按钮从来没有被禁用过，代码里连 `.disabled` 都没有。

但用户看到的现象是真的，只是原因在别处：**计划一创建，首次备份立刻就开始了**，向导文案也是这么承诺的。而备份进行中，这个计划的其他操作会被禁用。所以想改排除规则的人，只能眼看着一次用默认配置的完整备份先跑完，看起来就是「必须先备份一次」。

修法是在向导最后一步加一个「立即开始首次备份」的勾选框，默认勾上。

不过我在 [issue #42](https://github.com/shenxianpeng/keelhaven/issues/42) 里自己写的修法是错的。我说「不勾选时就别调用 `runDuePlans()`，反正 `SchedulePolicy.isDue` 本来就能处理从没跑过的计划」。它确实能处理，处理方式是立刻判定为该跑了：

```swift
guard let lastRunDate = plan.lastRun?.date else {
    return true          // 从没跑过 → 永远该跑
}
```

而调度器每 60 秒问一次，每次启动也问一次。按我说的改，最多把首次备份推迟一分钟，重启一次就照跑不误。实测确认了这一点：一个标记为「先别跑」的新计划，20 秒后 `lastRun` 已经写进去了。真正的修法得让计划自己记住「用户说了先别跑」。

### 向导只有三步，设不了排除规则、保留策略和验证周期

这条和上一条其实是同一个问题的两半。向导只携带五个设置，排除规则、验证周期、保留策略、性能参数一律取默认值，只能等计划建完了再去编辑窗口改。而首次备份在计划建完的那一瞬间就开始，所以这四项设置永远晚到一整次备份。

0.8.0 的做法是把编辑窗口里已经写好的四个区块抽出来做成共享视图，向导和编辑窗口两边共用，然后在向导最后一步加一个**默认折叠**的「自定义这个计划」。

折叠是关键。不想管这些的人看到的仍然是同样的三步，只多了一行字，不多一次点击，也不多一个决定。两个界面共用同一份代码，也就不会再各自漂移。

### 试运行

`restic backup --dry-run` 回答的是「如果现在备份，会存进去什么」，而且什么都不写。刚改完排除规则的时候，这个问题特别值得问一次。

0.8.0 里它是计划菜单里的「预览备份」。

有两个地方是故意做成分开的。第一，它在核心库里是一个独立的命令，不是给备份命令加一个布尔开关。预览这件事永远不该被持久化，而且任何一个想说「备份」的调用点，都不该因为传错一个布尔值而变成预览。两个命令的参数由同一个构造器渲染，所以预览不会在排除规则、标签或者限速上和它所预览的那次备份产生偏差，有一条测试专门断言两个参数数组去掉 `--dry-run` 之后完全一致。

第二，预览路径和真正的备份路径完全分开：它不写运行记录，不动健康状态那个圆点，不触发后续的校验和保留清理，也不发备份完成通知。

结果如果是空的，弹窗会直接说「与上次备份相比没有变化，现在备份也不会存入任何新内容」，再补一句「没有写入任何内容——这只是一次预览」，而不是打印「新增 0 个，变更 0 个，0 字节」让人自己去解读。

### 配置导入导出

这条还没做，[#44](https://github.com/shenxianpeng/keelhaven/issues/44) 开着。

不是因为不值得做，是因为它比看起来大。仓库密码、S3 secret key、REST 密码都在钥匙串里按计划 UUID 存放，单独导出的 `plans.json` 拿走是「死」的，导入之后每个计划都会报「钥匙串里没有该计划的密码」。而把密钥写进导出文件，直接违反这个项目的硬规矩。

还有几件事排在后面：源路径是绝对路径，换台 Mac 用户名和挂载点就变了；`plans.json` 是个裸数组，没有版本号，导入方没有任何可判断的依据；`lastRun` 这类字段是本机状态，导进去会立刻影响「该不该跑」的判断。

所以我在 issue 里把障碍和一个 v1 方案写清楚了，方案定下来再动手。

## 一位命令行老用户的清单

另一位用户从命令行 restic 迁过来，一封信列了他每天在用的参数。这大概是最有用的一类反馈：他没有说「你应该支持所有参数」，他说的是「这几个我天天用」。

**`--exclude-caches`** —— 跳过带 `CACHEDIR.TAG` 标记的缓存目录。放在排除规则旁边，因为它本质就是一条排除规则。

**`--one-file-system`** —— 不跨文件系统边界。这个在 Mac 上比听起来重要：你选的是一个文件夹，但真正被读取的是挂在它下面的一切。外置硬盘、网络共享、指向 `/Volumes` 的软链，踩坑的形态永远一样：本来只想备份「文稿」，结果悄悄开始拉一块 2 TB 的盘。界面上的文案我特意避开了「文件系统」这个说法，写成「不要备份挂载在这些文件夹里的其它磁盘」。

**`--skip-if-unchanged`** —— 内容和上一个快照完全相同时不创建新快照。这个带一个坑：跳过的时候，restic 的 summary 消息里**根本没有 `snapshot_id` 这个字段**。如果照着普通的成功备份去显示，就等于告诉用户「备份跑过了」，而实际上什么都没存。现在它会明确显示「与上次备份相比没有变化，因此没有创建新的备份点」，不会让用户以为这次真的存了东西。

**`--no-scan`** —— 这个没法直接加一个勾选框。

restic 正常会并发扫一遍源目录算出总量，就是为了能显示百分比。`--no-scan` 跳过这一遍，在慢盘或者网络文件系统上能省掉一整趟遍历，restic 自己的更新日志就是这么写的。

但我用真实的 restic 0.19.1 实测了一下，同一份源，开和不开各跑一次：

| | `percent_done` | `total_bytes` |
|---|---|---|
| 普通 | 0.79 → 1 | 有值 |
| 加 `--no-scan` | **每一行都是 0** | **字段不存在** |

而 App 是把这个值直接喂给进度条的。照做的话，进度条会整场停在 0%，然后突然跳到完成。对一个「备份期间唯一职责就是告诉你进行到哪」的菜单栏应用来说，这比它省下的那趟扫描更糟。

我在 issue 里列了三个选项，最后选了工作量最大的那个：开启这个选项时改用不确定进度条，下面显示实时字节数。`files_done` 和 `bytes_done` 这两个字段一直都在，所以「已备份 1.09 GB」既诚实又有用；一个卡在 0% 的进度条会被读成卡死了。

决定要不要显示百分比的是数据，不是那个开关：代码看的是 `total_bytes` 在不在。这样即使哪天 restic 改了省略字段的时机，那一行仍然是对的。

**`--keep-last`** —— 这位用户的整个保留策略就是「只留最近 N 个」，而 Keelhaven 表达不了。

原来的保留策略是三个预设：全部保留、一年历史、一个月历史。后两个里其实都带了 `--keep-last`，但被钉死在 3，而且总是和 daily / weekly / monthly 那一套一起出现。「只留最近 10 个，别的都不要」是够不着的。

预设的存在有它的理由：保留策略应该是一个人能读懂的选择。所以 0.8.0 加的是第四个选项：「保留最近 N 个备份」，旁边一个数字框，和三个预设并列。

数量在核心库里夹紧到 1–999，不信任存进来的值。测试专门走了 0、-1 和 `Int.min` 三个输入，因为一个数不对的保留策略如果渲染成一个空的 forget 参数，后果是删光。同样出于这个考虑，一个由更新版本写入、当前版本读不懂的保留策略，会退回到「全部保留」，而不是让整个计划列表读取失败。退化的方向得是不删东西的那一边。

## Backblaze B2 的坑，不是 App 能修的

还有人问 Keelhaven 支不支持 B2 的 hard delete，像 rclone 的 `--b2-hard-delete` 那样。

短答案是没有开关可以给你。但确实有件事需要告诉你，而我之前哪儿都没说。

`--b2-hard-delete` 是 rclone 自己的标志。restic 没有对应选项，因为它原生的 `b2:` 后端从 0.15.0 起就会删掉文件的所有版本，根本不需要这种开关。但 Keelhaven 是**通过 S3 兼容 API** 访问 B2 的（restic 官方文档也推荐这条路，原生 b2 库有错误处理问题），而 restic 的 S3 后端删对象时不传 VersionID，在 B2 上这只会把对象隐藏起来。旧版本会一直堆着、一直计费，`restic forget --prune` 也回收不了这部分空间。

解法在桶那一边：在 B2 的桶设置里打开生命周期规则「Keep only the last version of the file」。按 restic 文档的说法，旧版本会被隐藏一天，然后由 B2 自动删除。

所以 0.8.0 在这件事上做的是两处提示：网站 FAQ 加了一条 B2 专项说明，以及向导里当你填的 endpoint 含 `backblazeb2.com` 时直接显示一行提示，因为那里才是真会踩到的地方。

## 我没做的

**自由填写的参数输入框**。理由上面说过了，它不是「待办」，是「不做」。替代方案是具名字段，这两轮加进去的七个参数全是这么加的，每个都有自己的标签、校验和测试。[#45](https://github.com/shenxianpeng/keelhaven/issues/45) 一直开着当收集点：如果你有具体需要的参数，写下参数名和使用场景，够常用的就照同样的方式加进来。

**rclone 作为目的地**。有人提到 `-o rclone.program`。这个看着像一个参数，其实不是。它只在仓库地址是 `rclone:remote:path` 时才有意义，也就是说，这是一个「目的地类型」的需求，不是一个勾选框的需求。

障碍不在工作量，在模型冲突。rclone 的 remote 是在终端里 `rclone config` 配好的，存在 rclone 自己的配置文件里，还可能带它自己的加密密码。而 Keelhaven 的整个前提是密钥存在钥匙串里、明文不落盘。一个 Keelhaven 看不见也保护不了的凭据，我不确定应该由 Keelhaven 来「拥有」。

[#53](https://github.com/shenxianpeng/keelhaven/issues/53) 记录了这个请求。如果你需要的其实是某个具体的存储服务，欢迎去那里说是哪一个。B2、Wasabi、Cloudflare R2、Storj、iDrive e2、Scaleway、MinIO 这些都是 S3 兼容的，今天就能用。
